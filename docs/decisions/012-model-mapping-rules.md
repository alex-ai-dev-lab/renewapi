# ADR-012：直达模型映射规则与安全候选切换

日期：2026-10-02
状态：已采纳；实现与验证记录见 `docs/MODEL_MAPPING.md`。

## 背景

原 `model_mapping` 字符串中保存 JSON 字典。后端接受字符串或字符串数组，并递归展开别名；前端却只支持字符串值。同源多个目标无法在旧编辑器中无损编辑，首次添加的空行还会被自身值回传触发的重新解析删除。

简单放开重复来源不能解决持久化和执行问题：JSON 对象同名键会覆盖，已有候选推进 helper 又未进入真正的 relay 主循环。直接把所有旧映射改成一次替换，会破坏已有链式配置。

## 决策

### 1. 在已有 TEXT 内显式区分格式

- 保留外层 API 字段 `model_mapping` 为 JSON 字符串，不新增业务表或数据库列。
- 旧字符串/字符串数组字典保留原有递归解释。
- 新版采用 `{ "version": 2, "rules": [...] }`，每条规则有稳定 `id`、`from`、`to`、`priority`、`enabled`。
- 数值大的优先，同分保持数组顺序。来源与目标均可重复，运行候选稳定去重。
- v2 对当前映射输入模型进行一次精确匹配，不把目标再当作另一条规则来源。因此互映合法且不会递归。
- 未匹配时保留原有直通语义；客户、路由、映射、实际上游及计费模型的角色继续分开。

### 2. 不静默迁移或降级

旧记录打开或修改其它字段时不自动升级。显式升级先展开旧图，预览最终候选及顺序，再生成等价直达规则。循环、过深或超限旧图不能被猜测修复。

v2 不允许被旧客户端压回字符串字典或空串；清空用显式 `rules:[]`。必须先完成所有后端读取实例升级，之后才使用新格式。经典 UI 不应编辑其不理解的新格式。

### 3. 规则重试进入统一请求状态机

同渠道候选与跨渠道共享原有总尝试预算，不重置、不开嵌套无限重试，也不删除全局已尝试渠道集合以绕过保护。同渠道下一候选不计作真实渠道切换，但每次上游尝试都单独记录并计入总预算。

仅明确模型级拒绝和受控的模型容量错误允许推进候选。输出、usage、取消、严格绑定、已结算/退款、已受理任务和未知执行状态受到门禁保护。预扣为零不能被误判为已结算，使用只读账务状态接口判断；未知账务实现保持保守行为。

参数覆盖等后续处理若固定/改变实际模型，不能把配置上的 A/B 当成真正发送的两个不同模型。最终 wire 目标应被正确记录，并避免同渠道重复请求被覆盖为同一目标的候选。

本地结算只完成一次，不等价于保证上游未收费；不以“客户端尚未收到”推断上游没有执行。

### 4. 真正改写 outbound body

映射不能只改变 DTO 或日志字段。Chat-compatible/Responses 的 passthrough body 从可回放原请求构造，替换顶层 model，同时保留其它 JSON 字段与显式零值。保留 compact 的显式来源优先与严格路由约束，不强制反向修改响应模型名称。

### 5. 所有保存入口使用同一契约

新增、现代 If-Match 更新、旧 PUT 和标签批量更新统一校验。标签更新必须全部验证、同事务更新配置及能力，失败整批回滚。无 If-Match 的旧请求也需以预读版本绑定内部 CAS，不能用事务内的新版本为旧合并快照授权。

严格新写入拒绝重复 JSON 对象字段、无效类型/ID/优先级、空模型名及超限配置。已有异常旧值的读取与未改变该值的更新按兼容规则处理，不把无关字段更新当成强制迁移。

## 后果

- 多对一、一对多、交叉映射及显式优先级可以无损表示。
- 旧链式行为仍存在，需要维护双格式解析和明确的升级入口。
- 候选并非所有错误都自动切换；优先保证执行与费用边界。
- 需要真实主循环、HTTP 上游桩、实际请求体及 SQLite 账务测试，不能用 helper 单测代替。
- 模型名称和规则数量仍有资源上限；“不限唯一项”不表示无限请求或无限展开。
